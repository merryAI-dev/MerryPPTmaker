# Merry-slide Composition Format

Stage 2에서 만드는 `slide_plan.json`의 형식이다. 이 파일 하나가 CP3 프리뷰와 Stage 4A 빌더의 공통 입력이다.

프리뷰는 이 JSON을 실제 문구가 들어간 슬라이드로 렌더한다. 와이어프레임이 아니라 최종에 가까운 모습을 보여주므로, `content`를 비워두고 프리뷰를 띄우지 않는다. 빈 프리뷰는 검토 자료가 아니다.

## 최상위 구조

```json
{
  "title": "덱 제목",
  "slides": [ { "number": 1, "layout": "표지", "title": "...", "content": { } } ]
}
```

| 필드 | 설명 |
| --- | --- |
| `number` | 1부터 순차. 확정 저장 시 자동으로 다시 매겨진다 |
| `layout` | 아래 형식 이름 중 하나. **한글 이름을 그대로 쓴다** |
| `title` | 그 장이 증명하는 주장 한 문장. 명사형 제목이 아니라 액션 타이틀 |
| `content` | 형식별 구조. 아래 참고 |

## 형식 이름은 한글로 노출한다

내부 키(`two-col`, `section` 같은 영어 식별자)를 사용자에게 보여주지 않는다. 사용자는 그림과 한글 이름으로만 형식을 고른다.

| 형식 | 쓰임 |
| --- | --- |
| `표지` | 덱의 첫 장. 제목과 발행 주체 |
| `목차` | 전체 장 구성 |
| `간지` | 장이 바뀌는 구분 슬라이드 |
| `좌우 2단` | 두 내용을 나란히 비교하거나 이어서 |
| `표 중심` | 수치나 항목을 표로 정리 |
| `전폭 도식` | 구조나 흐름을 한 폭으로 크게 |
| `숫자 강조` | 핵심 수치 여러 개를 나열 |
| `단계 흐름` | 순서나 과정을 단계로 |

이 목록은 MYSC 레퍼런스 덱 32장을 분류해서 나온 것이다. 다른 톤의 덱에서는 Stage 0에서 받은 대표 장표를 기준으로 형식을 새로 정의한다.

## 본문 슬라이드 공통 필드

`좌우 2단`, `표 중심`, `전폭 도식`, `숫자 강조`, `단계 흐름`은 헤더 크롬을 공유한다.

| 필드 | 설명 |
| --- | --- |
| `content.section` | 좌상단 대분류 (예: `Ⅰ. 제안사 현황`) |
| `content.label` | 제목줄 앞 라벨 (예: `1-1. 기관 개요`). cyan으로 표시되고 `｜`로 제목과 이어진다 |
| `content.intro` | **리드 문단. 필수.** 아래 참고 |
| `content.note` | 슬라이드 하단 보조 설명 |
| `content.figure` | 이미지가 들어갈 자리. 아래 참고 |

### 리드 문단은 반드시 넣는다

구분선 바로 아래에 그 페이지 전체를 설명하는 문단이 들어간다. 레퍼런스 본문 슬라이드 **21장 전부**에 있는 요소이며(`y=1.503`, 12pt, 폭 10.336in), 빠지면 레퍼런스와 다른 덱이 된다.

- **길이는 50~100자.** 한 문장이나 두 문장으로 끝낸다.
- 제목줄을 되풀이하지 않는다. 제목은 주장이고, 리드 문단은 그 주장의 배경과 맥락이다.
- 아래 본문 블록에 있는 항목을 그대로 나열하지 않는다.

참고로 원본 레퍼런스의 리드 문단은 80~243자(중앙값 172자)로 더 길다. 50~100자는 더 압축된 기준이다.

### 이미지 자리는 비워두지 않고 명시한다

빈 공간이 남으면 `figure`로 무엇이 들어갈지 적는다. 프리뷰에 빗금 박스로 표시되어 어떤 이미지를 준비해야 하는지 알 수 있다.

```json
{ "figure": { "caption": "두 서버 연결 구조도", "hint": "화면 → Express → Spring Boot → 저장소" } }
```

`좌우 2단`은 `left.figure` / `right.figure`로 한쪽에만 넣을 수 있다. 나머지 형식은 `content.figure`를 쓴다.

### 슬라이드를 꽉 채운다

콘텐츠 영역은 세로 `2.18in ~ 7.62in`다. 표는 이 높이에 맞춰 행이 늘어나고, 도식 박스도 남는 공간을 채운다. 상단에만 내용을 몰아넣고 아래를 비우지 않는다.

내용이 모자라면 항목을 억지로 늘리지 말고 `figure`로 이미지 자리를 잡거나, 옆 장과 합친다.

## 형식별 content

### 표지

```json
{ "subtitle": "줄바꿈은 \n", "entity": "발행 주체" }
```

### 목차 / 간지

```json
{ "numeral": "Ⅰ", "items": ["소제목", "소제목"] }
```

`numeral`은 간지에서만 쓴다.

### 좌우 2단

```json
{
  "label": "1-1. 소분류",
  "left":  { "pill": "왼쪽 소제목", "body": ["항목", "항목"] },
  "right": { "pill": "오른쪽 소제목", "body": ["항목", "항목"] }
}
```

한쪽에 6개를 넘기지 않는다. 넘치면 장을 나눈다.

### 표 중심

```json
{
  "label": "2-1. 소분류",
  "pill": "표 제목",
  "table": { "headers": ["구분", "A", "B"], "rows": [["행", "값", "값"]] },
  "note": "표 아래 보조 설명"
}
```

### 전폭 도식

```json
{
  "pill": "도식 제목",
  "flow": [ { "head": "단계명", "body": "설명\n줄바꿈 가능" } ],
  "note": "도식 아래 보조 설명"
}
```

`flow` 항목 사이에 화살표가 자동으로 들어간다. 3~4개가 적당하다.

### 단계 흐름

```json
{
  "pill": "흐름 제목",
  "steps": ["1단계", "2단계", "3단계", "4단계"],
  "note": "흐름 아래 보조 설명"
}
```

`steps`는 chevron으로 그려진다. 레퍼런스에 화살표 커넥터가 없으므로 선으로 잇지 않는다.

### 숫자 강조

```json
{
  "stats": [ { "label": "지표명", "value": "256", "unit": "개", "note": "산출 근거" } ],
  "note": "아래 보조 설명"
}
```

카드 배경을 넣지 않는다. 라벨 → 큰 숫자 → 각주 순서로 쌓는 것이 레퍼런스 문법이다.

## 검증

프리뷰 생성 시 알 수 없는 형식 이름은 `unknown_formats`로 보고된다. 비어 있어야 한다.

```bash
node scripts/preview-composition.mjs --plan slide_plan.json --out preview.html
```
